# Testing

Local test runner. `Tools/_WF/Testing/test.ps1` builds once, then runs `Content.Tests` and
`Content.IntegrationTests` straight from `bin/` with `--no-build`, server GC and eight NUnit workers, with
`EntityTest` in a second process alongside. The whole suite (5,400 integration tests, CI's set without
`ShipyardTest`, plus 2,050 unit tests) takes about 12 minutes on a 12700K with 64 GB, against 38 minutes for a plain
`dotnet test`. Results go to `test_results/` (git-ignored).

```powershell
Tools/_WF/Testing/test.ps1                     # build, then the whole suite
Tools/_WF/Testing/test.ps1 -Test MyFixture     # one fixture or test by name substring
Tools/_WF/Testing/test.ps1 -NoBuild -Unit      # Content.Tests only, 15 s
Tools/_WF/Testing/test.ps1 -Workers 4          # fewer server/client pairs on a smaller machine
```

Why each piece is there, with the measurements behind it:

- **`--no-build`**: `dotnet test` re-evaluates the whole project graph on every call, about 20 s even when nothing
  changed. The script builds once and runs every suite from `bin/`.
- **Server GC** (`DOTNET_gcServer=1`, `DOTNET_GCConcurrent=0`): the test host runs several server/client pairs in one
  process, and every pair allocates hard. With workstation GC each collection stops all of them, so 8 workers ran
  the suite in 34 min against 38 min for 2, with the host busy on about one core. Server GC gives each core its
  own heap: the same 1,478-test subset went from 14 m 37 s to 6 m 18 s, and non-concurrent GC took another 6 %
  off. Set in the script's environment, so CI's 2-core runners are untouched.
- **`NUnit.NumberOfTestWorkers=8`**: `Content.IntegrationTests/AssemblyInfo.cs` caps parallelism at 2 for CI. Each
  worker keeps one pair alive (2 to 3 GB and about two busy threads). 8 saturated the 12700K; 12 was no faster and
  used a third more memory.
- **`EntityTest` in its own process**: it is `[NonParallelizable]` because its spawn-everything tests need about
  6 GB each, so NUnit runs it alone after everything else, which left 7 workers idle for the last 5 to 10 minutes
  of every run. As a second process it runs beside the rest and finishes in under 5 minutes.
- **`PrototypeTests` is `[Parallelizable(ParallelScope.All)]`**: its four tests take 2 minutes each and have no
  shared state; in sequence they were the longest chain in the suite.
- **`NUnit.Where`, not `--filter`**: a `--filter` exclusion only hides results; NUnit still runs the tests.
  `NUnit.AssemblySelectLimit` is raised because above 2,000 selected tests the adapter silently runs the whole assembly.
- **One run, many tests**: the pooled pair takes about 45 s to start and is reused by every test in the same run.
  Running tests one at a time pays that start-up each time.
- **First run after a build is slow**: Windows Defender scans every fresh DLL on load, which turned a 7 s discovery
  into 78 s once. Excluding `bin/` and `RobustToolbox/*/bin` from real-time scanning removes that (a system setting;
  do it yourself).

What did not help: more than 8 workers (CPU-bound), and the GPU (no renderer runs in the test client; the work is
branchy single-threaded .NET per pair).
